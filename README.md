# 兰州大学校园网自动认证（eLearning）

兰州大学（LZU）校园网的自动登录工具，针对深澜 **srun V1.18** 认证系统。

兰大主要有两个官方无线网络：**`LZU`** 和 **`iLZU`**。连上任意一个，完成认证即可上网。
问题在于认证态并不稳固 —— 断电、路由器重启、PPPoE 重拨、长时间离线，都会让认证态失效，
表现就是"昨天还好，今天开机上不了网，得手动开认证页再登一次"。
本项目把这步自动化，并额外处理了账号被其他设备占用的情况。

两套实现，按你的场景选一套：

| | 电脑端 | 路由器端 |
|---|---|---|
| 语言 | Python 3（纯标准库，零依赖） | Lua 5.1 |
| 认证对象 | 当前这台电脑 | 路由器自身 |
| 触发方式 | 开机后跑 9 次（约 35 分钟）自动退出 | 常驻轮询，不依赖电脑 |
| 适用场景 | 普通用户，只连 `LZU` / `iLZU` 两个官方无线网 | 宿舍/出租屋有 OpenWrt 路由器，想让全屋设备一起上网 |

两套共用同一套协议实现与同一套判活、解绑策略，协议层输出**逐字节一致**。

## 两种方案怎么选

**电脑端 —— 适合绝大多数人。**
装个 Python 就能跑，只影响你自己这台电脑。把 `target_ssids` 设成 `["LZU", "iLZU"]`，
脚本就只在连接这两个官方无线网时才动手，连其他网络（家里 WiFi、手机热点）一律跳过，
不会误操作。每次开机集中跑一轮，跑完即退，不常驻、不后台轮询。

**路由器端 —— 适合有 OpenWrt 路由器的情况。**
校园网的认证态本质上是绑在**出口 IP** 上的，不是绑在某一台设备上。所以让路由器自己完成
认证之后，整个局域网就共享这一个已认证的出口：手机、平板、电脑、电视连上路由器的 WiFi
就能直接上网，**不需要每台设备各自登录**，也不用担心电脑关机后网络跟着断掉。

换句话说，路由器端把"认证"这个动作从"每台设备各做一次"变成了"整网共享一次"，
这是它相比电脑端最实际的价值。前提是路由器已开 SSH，且具备 `lua`、`socket.http`、`cjson`
（OpenWrt 18.06 一般都有，本项目在小米 CR8809 上验证）。

## 为什么是 eLearning（@study），不是 iLZU 无感知认证

学校提供两种上网方式，取舍很明确：

| | iLZU 无感知认证 | eLearning（@study） |
|---|---|---|
| 认证方式 | 首次账密认证后把设备 MAC 绑定，之后自动放行 | 每次都要账密 + 挑战应答 |
| 流量 | **每月 30GB** | **不限量** |
| 掉线情况 | 绑定后基本不掉了 | 断电、重拨、被别的设备占用都会掉 |

无感知认证确实省事，但流量有上限。要用不限量的那档，就只能走 eLearning；而 eLearning 的
认证态是绑定在**出口 IP** 上的单次会话，断一次就得重新认证一次。

**所以本项目要解决的不是"懒得输密码"，而是"想用不限量的 eLearning，却受不了它反复掉线"。**
这也是它和那些做无感知认证 / 只是定时重登的脚本的根本区别 —— 后者绑定一次就长期有效，
本项目要处理的是每次掉线之后怎么把会话快速抢回来，包括账号被别的设备占用的情况。

## 认证态为什么会消失

认证态绑在**出口 IP** 上，本质上是一次会话，不是一份保存在设备里的凭据。所以它会消失：

- 路由器断电、重启、PPPoE 重拨 → 出口 IP 变了 → 旧会话作废
- 长时间不在线 → 服务端清掉会话
- 同一账号在另一台设备上用 eLearning 方式登录 → 单会话策略把这边顶掉

第三种最容易踩坑：你自己什么都没做，网就断了，因为手机或另一台电脑把账号占走了。
电脑端和路由器端都实现了自动处理这条 —— 先尝试登录，确认是被占用之后才去注销占用者，
再进行重登，不会出现"自己把自己踢下线再自己解开"的循环。

## 快速开始（电脑端）

```bash
cp config.example.json config.json      # 填入账号密码
python lzu_auto_login.py --once         # 跑一次：已在线直接退出，未在线才登录
python lzu_auto_login.py --boot         # 开机守护：9 次后自动退出
python lzu_auto_login.py --test         # 只打印当前状态，不改动网络
```

Windows 开机自启（可选，本项目不再附带现成脚本，自己建一个即可）：把下面存成
`lzu.vbs`，放进 `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\`；
或者用任务计划程序以"登录时"为触发器直接调 `python lzu_auto_login.py --boot`。

```vbs
CreateObject("WScript.Shell").Run """pythonw.exe"" ""D:\path\to\lzu_auto_login.py"" --boot", 0, False
```

`0` 表示隐藏窗口，`pythonw.exe` 不弹控制台。路径记得换成你本机的位置。

## 快速开始（路由器端）

适用于已开 SSH 的 OpenWrt 18.06 设备（本项目在小米 CR8809 上验证）。需要 `lua`、`luac`、
`curl`、`openssl`，以及 Lua 的 `socket.http` 与 `cjson`。

```bash
# 1. 配置路由器密码（该文件已被 .gitignore 排除）
echo '{"host":"192.168.10.1","user":"root","password":"你的路由器密码"}' > router/.router_auth.json

# 2. 一键部署：上传 + 生成配置 + 语法检查 + 协议自检 + 装开机自启
python router/deploy.py --service

# 3. 查看
ssh root@192.168.10.1 "tail -f /overlay/lzu/lzu_auth.log"
```

单文件手动部署也行：把 `router/*.lua` 和 `config.json` 放进 `/overlay/lzu/`，
再把 `router/lzu_auth.init` 复制为 `/etc/init.d/lzu_auth` 并 `enable`。

## 工作原理

```
每轮：探测外网（校验响应正文）
  ├─ 通 → 睡眠（间隔 60→120→300→600→900 秒递增）
  └─ 不通 → 连续 2 次才确认掉线 → recover()
                ├─ 服务端说已认证但探测不通 → 注销该会话后重登
                ├─ 查询失败               → 跳过本轮
                ├─ 确认未认证             → 直接登录
                └─ 登录失败且疑似占用      → 注销占用会话后重登
```

几个刻意的设计：

- **不 ping。** 未认证时 ICMP 可能仍通，会误判为已联网。改成 HTTP 请求并校验正文，
  被劫持到认证页就判为不通。
- **`login_ok` 不算成功。** 服务端返回成功但实际不通是常有的事（会话挂在别的 IP 上），
  必须探测确认能上网才算成功。
- **先登录，后解绑。** 绝不预先解绑，避免"自己把自己踢下线再自己解开"的死循环。
- **解绑用 `srun_portal action=logout`。** 该接口按 `ip` 参数查会话，不校验请求来源，
  因此未认证的设备也能注销指定 IP 的会话。代价是需要先通过自助服务（账密 SSO）
  列出账号下有哪些在线设备。

## 配置项

见 `config.example.json`，每一项都有说明。最关键的几个：

| 键 | 作用 |
|---|---|
| `username` / `password` / `domain` | 账号密码与域。`@study` 对应 eLearning（流量不限），空串对应 `@lzu.edu.cn` |
| `target_ssids` / `ssid_filter` | 只在指定 WiFi 下工作，避免在别人家也去连 Portal |
| `auto_release` / `release_cooldown` | 是否自动踢掉占用者，以及两次解绑的最小间隔 |
| `internet_probe_urls` | 联网验证用，被劫持到 Portal 即判未通 |

也可以用环境变量 `LZU_USERNAME` / `LZU_PASSWORD` 覆盖账密，`LZU_CONFIG` 指定别的配置文件。

## 安全提醒

- **`config.json` 含明文密码，已被 `.gitignore` 排除。** 不要提交它。
- 路由器部署用的 `router/.router_auth.json` 同理。
- 自动解绑会踢掉同账号下的其他设备（手机、平板）。这是校园网单会话策略的必然结果，
  不想要就设 `auto_release: false`。

## 适用范围与已知限制

- **主要面向 `@study`（eLearning）账号。** 该账号并发会话数为 **1**，任意两台设备都会
  互相顶掉，这正是解绑功能存在的场景。
- **普通账号（`@lzu.edu.cn` / `@ilzu`）据说是 3 个并发名额**，那样就很少撞上 `E2620`，
  解绑功能基本用不到。这一点我们没有复核过，拿不准的话把 `auto_release` 设为
  `false` 更稳妥。
- **无感知认证与本项目是否冲突，不知道。** 学校系统更新后支持无感知认证（把设备
  MAC 绑定到账号，之后自动放行）。已知的一点是：**如果把无感知认证绑定在路由器上，
  那么即使断电重启、重新拨号，路由器也会自动认证上，那种场景完全不需要本项目。**
  但无感知认证与本项目的注销、重登逻辑同时存在时会不会互相干扰，我们没测过，
  也说不准。
- 电脑端只在 `target_ssids` 列出的无线网下工作；路由器端要求能访问内网 Portal。
- 流量配额（如 iLZU 每月 30GB）由学校规定，可能随时调整，以官方为准。
